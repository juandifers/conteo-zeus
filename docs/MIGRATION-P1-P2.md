# Migrating P1 data into a P2 build

P1 is in production use. Every tablet that has run it holds Dexie rows this
build has to keep reading, and every session in there carries `ExportRecord`s
naming the counts, the coverage and the SHA-256 of a file somebody uploaded into
an ERP.

**The rule this document exists to state: a P1 session folds to the same numbers
after the upgrade as before it.** Not approximately, not for the common cases —
item by item. A session that folds differently is a session whose export record
no longer describes it, and afterwards there is no way to tell which of the two
numbers Zeus received.

Proved by `tests/domain/migration.test.ts` against
`tests/fixtures/p1-log.json` and `tests/fixtures/p1-expected.json`. The
expectations were **generated by the P1 fold before the P2 changes landed**.
They are not a transcription of what the P2 fold happens to do, and regenerating
them to make the test pass would delete the only evidence of what P1 did.

---

## What a P1 event is missing

Three things, and each gets a rule rather than a default.

### 1. No `counterId`

`CountEventBase.counterId` is new and is **not** `usuario`. It is optional on
the type, which is an accurate description of the database: the rows that are
already there do not have one.

**Rule: a P1 event is never hashed.** `canonicalEvent` throws
`UnchainableEventError` naming the event rather than falling back to `deviceId`
or to `usuario`.

Falling back would look kinder and is worse. It would mint a chain that never
existed, over events nobody ever chained, and produce a `headHash` a server
could be persuaded to accept as a counter's manifest. The chain's whole value is
that a head means "these exact events, in this order, from this counter"; a head
computed from a substitute id means "these events, plus a guess".

The consequence is small because of the next rule.

### 2. P1 sessions are not migrated onto the server

They stay **local, read-only and exportable exactly as they are today**. No
upload path, no `session_id` in Postgres, no counters row.

This is deliberate and it is the reason rule 1 costs nothing. A P1 session is a
finished count of one bodega taken on one tablet; there is nothing for a
multi-device server to do with it, and putting it there would mean inventing a
counter, a chain and an assignment for a count that had none. What the tablet
can still do — fold it, review it, generate the `.txt`, hash the bytes, record
the export — it still does, on exactly the code path it always used.

### 3. No `retractsEventId`

This is the one genuine semantic break, and rule 4 of the fold is what contains
it.

`RetractEvent.retractsEventId` is now the normal shape: a withdrawal names the
one event it takes back. Under several counters the old whole-item semantics are
a data-loss bug — Ana retracting her own mis-tap on article 4471 would silently
discard Luis's count of the same article.

**Rule: a retraction with no `retractsEventId` keeps P1 semantics exactly.** As
of that event the item is untouched and the running value is cleared, so a later
`add` starts from zero. Every P1 retraction is one of these, so every P1 fold is
unchanged.

The fold does this in four steps (`src/domain/fold.ts`):

1. collect `retractsEventId` from every scoped retraction into a set;
2. drop every event whose `id` is in that set, and drop the scoped retractions
   themselves;
3. fold the survivors under the existing rules;
4. an unscoped retraction inside those survivors behaves as it did in P1.

A P1 log contains no scoped retractions, so steps 1 and 2 are no-ops on it and
step 3 hands the whole log to the same fold P1 ran.

## What deliberately *does* change, and why it is not a migration break

### `undoLast` no longer appends `add(-q)`

Undo is now `retract(the last standing event)`. The `add(-q)` special case is
gone.

This changes no stored number. Undo is an **action taken now**, not a replay of
stored data: the events already in the database fold exactly as before, and what
changed is which event the next tap appends. `add(-q)` restored the prior
*value* and not the prior *state* — undoing the first tap of a tally with
`add(-1)` landed on `counted 0`, a write-off of the whole book figure. Now that
a withdrawal can name its target, the substitute is strictly worse than the thing
it substituted for.

Undo still works on P1 events. Withdrawing one by `id` needs nothing the event
does not already carry.

### Undo can target an unscoped retraction

The "descartar conteo" button writes P1's whole-item withdrawal, and undoing it
has to bring the count back or the button is one-way. A **scoped** retraction is
never a target — the fold drops it, so withdrawing one would change nothing, and
resurrecting an undo would make the answer depend on arrival order. An
**unscoped** one is a target, and withdrawing it by name restores everything it
took, because the fold then never sees it.

That is not the reversal DOMAIN.md §6 rules out. That was a *clock* silently
overriding somebody's decision. This is the person who made the decision naming
it, order-independently, with no clock involved.

### `compareEvents` gained a same-counter branch (P2.3)

The fold now orders two events by `seq` alone when they carry the **same**
`counterId`, and by `(at, deviceId, seq, counterId, id)` otherwise. See
DOMAIN.md §3 for why.

**P1 events have no `counterId`, so the first branch never fires for them.** A
P1 log therefore sorts exactly as it did, which is not an argument — it is what
`tests/domain/migration.test.ts` re-checks against `p1-expected.json`, a fixture
generated by the P1 fold before any of this landed. That test is the reason it
was safe to change the comparator at all; the fixture is not to be regenerated.

The one shape worth naming is a mixed log: a P1 event and a P2 event in the same
session. It cannot occur — a P1 session is never dispatched and a P2 session is
never counted by the P1 app (§2) — and if it did, the events would compare
through the second branch, since `undefined !== 'counter-ana'`.

### The `ZONAS` picker was removed (P2.3)

`loadZona` / `saveZona` / `ZONAS` are gone from `src/ui/identity.ts`, and the P1
count screen no longer has a zone dropdown. New P1 events carry `zona: ''`.

**No stored event changes.** `zona` is stamped at append time and read back
verbatim; the events already in the database keep whatever zone they were
stamped with, and the debug export still prints it. Nothing is written back from
this field either — `ubicacion` stays empty (ZEUS_FORMAT.md §9) — so the loss is
a label on future P1 events and nothing else.

It is worth being plain that this *is* a small P1 regression accepted for a P2
reason: a zone somebody picks off a list and a zone derived from the assignment
cannot both be the source of one field (DOMAIN.md §6.1), and P1 has no
assignment to derive one from.

### `validateEvent` grew three checks

Non-finite quantities, control characters in a `note`, and a null `idarticulo`
on a kind that is not session-scoped.

**None of them may reject data that is already in the database**, and the
migration test asserts that by re-appending the whole captured P1 log through
`MemoryRepository`. An event that cannot be re-appended is an event that cannot
be restored from a backup.

## Still to do, and deliberately not done here

**`store.retract()` still writes an unscoped whole-item withdrawal.** On a
single device that is correct and it is what "descartar conteo" means today.
Under several counters it is the data-loss bug described above.

**P2.2 closed it, and closed it by removing the action rather than rescoping
it.** Under several counters "descartar conteo" means "discard everyone's count
of this article", which is never what the person tapping it intends, so there is
nothing to rescope it *to*: undo already withdraws the counter's own last
standing event by name, and that is the only withdrawal the P2 counter path
offers. The button is now rendered only where the action exists —
`CountStore.offersWholeItemDiscard`, false whenever a `counterId` is present —
and a permanently disabled control was rejected on the way, because a dead
button is an action somebody keeps trying.

The unscoped retraction stays in the domain and in the fold, reachable by P1
sessions and by them alone. `tests/gate.test.ts` asserts no P2 source constructs
one; `POST /api/c/:token/events` answers `422` if one arrives anyway, because a
cached PWA build from three weeks ago is a client this repository does not
control.

**`counterId` is written from P2.2, on the counter's path only.** A `CountStore`
opened with a `counterId` stamps it on every event, chains each one and writes it
through the outbox; a store opened without one is P1's and is unchanged in every
respect. The two coexist in one class and one Dexie table on purpose — the fold,
the undo rule and the halt behaviour are the same behaviour, and a second copy of
them would drift.

**`seq` means something different on the two paths.** P1's is one *device's* own
numbering, from `DeviceRow.lastSeq`, shared across every session that device has
ever held. A P2 `seq` belongs to the **counter**, starts at 1, and continues
across the spare tablet somebody picks up when the first one dies — which is why
`countEvents` gained `[sessionId+counterId+seq]` beside P1's
`[sessionId+deviceId+seq]` rather than replacing it. One-based because the finish
manifest and the push protocol both need a value meaning "nothing yet", and both
spell it `0` (DOMAIN.md §6.2).

**P2.1 did land the other half of `zona`.** A section's name is the zone, fixed
before anybody counts (DOMAIN.md §6.1), and a prepared tablet holds its sections
already grouped. Nothing reads that yet on the counting side — the entry screen
is P2.3 — so `src/ui/identity.ts` still offers `ZONAS` as a dropdown for the P1
flow. Those two must not both survive P2.3.

**`note`, `finish` and `reopen` gained their write path in P2.2**, on the P2
store only: `store.finish()`, `store.reopen()` and `store.note()` refuse outright
when no `counterId` is present, because those events belong to a counter and a P1
session has none.

## Dexie

No schema migration was required for P2.0, and `src/store/db.ts` was unchanged
by it: the new fields are optional or new-kind-only, and IndexedDB stores
whatever shape it is handed.

P2.1 adds **v5**, one new table (`counterAssignments`) and nothing else. No
existing store is touched, so a tablet holding an unposted P1 count opens v5
with that count intact — which is the rule the version block in `db.ts` states
and the reason the change is an addition rather than a reshaping.

P2.2 adds **v6**: three optional fields on `countEvents` (`prevHash`, `hash`,
`sync`) and two compound indexes over them. Again an addition — no table is
reshaped, and a P1 row simply has none of the three, which puts it outside both
new indexes because IndexedDB skips a record whose index key is undefined. That
is the wanted behaviour: a P1 event has no chain and is never pushed anywhere.

**The outbox is `sync === 'pendiente'`, a query over that one table**, and not a
second store. Two tables that can disagree about what happened is the failure
this architecture exists to avoid, and an outbox is exactly the shape that
disagreement takes: a queue holding an event the log does not have, or a log
holding an event the queue forgot to enqueue. One consequence for the P1 side is
that `localStorage`'s lifeboat (`src/ui/outbox.ts`) is **not** used on the P2
path — it replays through `appendEvent`, which writes no chain metadata, so a
replayed event would land unhashed and unpushable.

One consequence is worth stating because it is load-bearing and it is not
obvious. `countEvents` is indexed on `[sessionId+idarticulo]`, and IndexedDB
will not accept `null` as a key component: a record whose `idarticulo` is null
is silently **absent from that index** while remaining in the store. So a
`finish`, a `reopen` or a session-wide `note`

- comes back from `eventsForSession`, which queries `sessionId`, and
- does **not** come back from `eventsForItem`, which queries the compound index.

That is exactly the behaviour wanted — a `finish` is not an item's event, and
`resolve` throws if one reaches it — but "exactly what we wanted, by accident"
is not a guarantee. `tests/store/sessionScoped.test.ts` asserts it against the
real adapter, so a future index change cannot quietly start feeding
session-scoped events into the item fold.

P2.3.5 adds **v7**: one more index on `countEvents`, `sync` on its own. v6's
`[sessionId+counterId+sync]` cannot answer «which counters on this tablet still
have a queue», because it is keyed by counter first and there is nothing to look
up until you already know the answer — and the whole point of that question is
that the counter with the queue may be somebody who went home (DOMAIN.md §6.4).
An index addition, so a row written under v6 is re-indexed on upgrade and a
queue that predates the feature is visible to it. P1 rows have no `sync` at all
and stay outside it, which is right: they are never pushed anywhere.

The version bump belongs with the write path that first *uses* the fields
(P2.1), where there is something to migrate to.

## What P2.3.5 does *not* change for a P1 session

Nothing. It is worth saying explicitly because the task is about counters
changing hands, and a P1 session has no counters in the P2 sense — no partition,
no assignments, no tokens, and therefore nothing to reassign.

- **`retirado` is unreachable.** It is a state on `counters`, and a P1 session
  has no rows there.
- **`session_actions` stays empty**, for the same reason: there is no admin, no
  dispatch and no server-side session to hang one off.
- **`yaRegistrados` never arrives.** It is a field on the assignment payload, and
  a P1 session has no payload. `catalogueOf` reads it as `?? []` anyway — not for
  P1's sake but for a **P2 tablet prepared before the field existed**, which is a
  real device sitting in a drawer over a deploy and has to open with what it
  holds.
- **The fold is untouched.** `tests/domain/migration.test.ts` folds the P1
  baseline log to the same 298 resolutions it did before, which is the check that
  makes every change in this task safe to have made.

## What P2.4 does *not* change for a P1 session

Also nothing, and it is worth stating because P2.4 is the first task that touches
the **waiver**, which is a P1 concept that predates all of this.

- **P1's own waivers are untouched.** `CountStore.markUnchanged` and
  `waiveMany` go on writing `unchanged` **events**, and a P1 session's review
  screen goes on reading them. The fold's rule for `unchanged` has not changed a
  line.
- **P2's waiver is a different thing with the same fold effect.** It is an action
  on `session_actions`, projected into `unchanged` events on every read
  (`waiversToEvents`) and stored as an event nowhere. The projection is scoped to
  articles that fold to `untouched` from counter events alone, which is what
  makes it order-independent; P1's event-shaped waivers were written by the one
  device that also held the counts, so the question never arose for them.
- **Nothing back-fills.** A P1 session has no `session_actions` row and needs
  none; its waivers are already in the log where they have always been.
- **The review module is new and reads a P1 session fine** — it takes items,
  events, actions and counters, and a P1 session simply has no actions and no
  counters. Every event it holds is attributed to `sin contador`, which is what a
  session with no counter identities is.

## What P2.5 does *not* change for a P1 session

Nothing, and this time the reason is structural rather than careful: **a P1
session cannot be sealed at all.** Sealing is a server operation over
`sessions`, `counters` and `session_actions`; a P1 session lives in the device's
own IndexedDB, was never uploaded, and has no row anywhere the seal could write
to.

- **P1's export is untouched.** `generateAdjustment` → `exportAdjustment` →
  `uncountedPolicy: 'reject'` is still the path the P1 review screen takes, still
  refuses a file with an uncounted row in it, and still runs `verifyWriteBack`.
  `writeAdjustment` is a second function beside it, not a replacement — see
  DOMAIN.md §6.6 for why the two policies differ and what pays for it.
- **`sessionHash` changed shape and no P1 session ever had one.** It now covers
  `sourceHash` and each chain's length as well as its head. Nothing recomputes an
  older digest, because P2.5 is its first caller and no `session_hash` was ever
  written before it.
- **A P1 log has no chain to verify.** Its events carry no `counterId`, so
  `canonicalEvent` refuses to hash one (`UnchainableEventError`), which is the
  same refusal that has been there since P2.2. The verifier is for sealed P2
  sessions; handed a P1 export it would have nothing to check, which is why the
  bundle is served from `sellado` onwards and not from anywhere else.
